\subsection{Reliability scoring}

Image-differencing searches for transients typically contend with high rates of false positives.
Among the raw detections, artifacts may dominate real astrophysical sources by an order of magnitude.
These may be due to imperfectly-corrected instrument signatures, astrometric mismatches between the template and the science image, cosmic rays, or algorithmic failures in the differencing.
Modern surveys employ machine-learned classifiers to winnow these candidates \citep[e.g.,][]{Bailey:07:NearbySNFML,Bloom:12:RealBogus,Brink:13:RB2,Wright:15:PS1ML,Goldstein:15:DESRealBogus,Duev:19:Braii}.
These have steadily improved in performance and sophistication as the classifiers transitioned from Random Forest models trained on manually-constructed feature sets to deep neural networks trained directly on image pixels.
Some approaches have combined both detection and scoring without using the difference image \citep{Sedaghat:18:Transinet,Acero-Cuellar:23:NoDifference}.

\citet{DMTN-337} describes the training and performance of the reliability classifier versions deployed in Alert Production.

\subsection{Source Association}

Due to AP's real-time nature, it is not possible to perform \textit{post-facto} source association as in the annual data releases.
Instead, spatial association is performed on-the-fly by the \texttt{DiaPipelineTask} within the \texttt{lsst.ap.association} package.
A dedicated Alert Production Database (APDB; \S \ref{sec:apdb}) holds the current state of the system.

During the preload step (\S \ref{sec:preload}), DIAObjects and SSObjects overlapping the expected field of view of the image are stored in the local prompt processing worker butler repository.
The new DIASources are first spatially associated with the existing DIAObjects by finding the closest match within a maximum distance of one arcsecond.
Pairs with the closest spatial separations are joined first to minimize misassociations.
When a match is found, the DIASource is added to the DIAObject's list of measurements.
Unassociated DIASources are then spatially associated with the predicted positions of the SSObjects at the time of the exposure.
For DIASources with no matching DIAObject or SSObject, a new DIAObject is created and the DIASource is added to it.

\subsection{Alert Distribution} \label{sec:alertdist}

We use the Kafka distributed streaming platform\footnote{\url{https://kafka.apache.org/}} to transmit alerts to brokers.
Kafka provides a fault-tolerant, low-overhead mechanism to transmit large volumes of data to multiple consumers and is widely used both in industry and in astronomy. 
\eric{cite patterson, GCN, Hopskotch, other Rubin usage...}

The Alert Distribution Kafka system is deployed at the USDF using Kubernetes.
\bri{details of the deployment}

The Alert Distribution system is deployed via helm charts within the Sasquatch application, Rubin's Telemetry Service application.
It is split into several different Helm charts which manage the deployment, `strimzi-kafka`, `alert-brokers', and `alert-database`.

Within the `strimzi-kafka` chart, the Kafka nodepool, the controllers, and the kafka setup itself are managed. Alert topics and
users are managed through the `alert-brokers` Helm chart. In the strimzi-kafka chart, the number of internal brokers is managed, the
resource usage, and

We manage Alert Distribution specific configurations in the `values-usdprod-prompt-processing.yaml', which uses the existing templates
and configures them for the Alert Stream system.

The Alert Database Ingester, which writes all alerts to the Alert Archive, is managed in `alert-database'. The ingester
is an internal Alert Stream consumer, which reads the alerts in the current alert stream topic and writes them
to the Alert Database Archive.

\bri{schema management}
 The Confluent Schema Registry allows us to maintain a version history of the alert schemas. The schema registry is published to
 `rubin-alert-schemas.slac.stanford.edu`.

The alert packets do not contain their own schemas. Instead, the associated schemas are stored in a Confluent Schema Registry.
 When serialized via fastAvro, each packet is given a magic byte of 0, which indicates it is Confluent Avro wire format v0.
 The next 4 bytes indicate the schema ID. This is the ID in the schema registry associated with the packets specific schema version.
 To maintain consistency, we relate the schema version and schema ID. We follow a pattern where the schema ID is the version number encoded as an integer without the decimal point.
 Schema version 10.0 would be given the schema ID 1000, schema version 10.1 would be schema 1001, and schema version 10.12 would be schema ID 1012 and so forth.
 This allows for up to 99 minor versions within any major schema version. These schemas are synced to the schema registry via the
 `alert-stream-schema-sync` chart, which loads in the schemas upon syncing the Alert Stream application within ArgoCD.

Because of the large size of the alert packets and the short latency requirement, bandwidth out of the US Data Facility (USDF) at SLAC limits the number of direct recipients of the full alert stream.
Seven community alert brokers receive the full alert stream directly from the USDF. (\S \ref{sec:brokers}).
